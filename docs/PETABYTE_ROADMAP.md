# Arctic-Proxy → Petabyte-Scale L4 Proxy: Engineering Roadmap

## 1. Executive Summary

Arctic-proxy is a clean, correctly-architected single-upstream TCP relay (per-CPU pinned workers, SO_REUSEPORT, current-thread runtimes), but it is **structurally three-to-four orders of magnitude short of its stated "millions of connections / multi-100-Gbps" goal**, and it carries two latent self-DoS bugs that would take it down in production well before scale even matters. The hardest ceiling is physical: every connection dials one hardcoded upstream `(dst_ip, dst_port)` from one source IP (`handle_connection`, src/main.rs:540-554), capping the entire proxy at the ~28k–64k ephemeral-port limit regardless of cores or `max_connections`. The most dangerous bugs are the total absence of any idle/data-phase timeout on the relay (`io::copy_bidirectional` at src/main.rs:561 has no deadline) — a trivial slowloris connection-exhaustion DoS — and the reject-path `sleep().await` inside the single-threaded accept loop (src/main.rs:390-392) that throttles the proxy's *own* recovery under overload. The highest-leverage moves are: **(a)** add idle/lifetime timeouts + fix the reject sleep + make the conn-counter panic-safe; **(b)** turn the single upstream into a resolved backend pool with health/failover/retry; **(c)** wire `buffer_size` into the copy path (or splice) and CPU-align accepts. Beyond incremental work, true zero-copy and line-rate-per-core require an **io_uring/glommio architectural fork**, which is the one large rewrite worth scoping separately.

## 2. Prioritized Roadmap (ranked by impact_at_scale / effort, grouped by tier)

## 3. First-PR Recommendation (3–5 highest-leverage changes)

Land these together — all are small/trivial, touch one file, ship no architectural risk, and each closes a correctness hole or a documented-but-fake knob:

1. **Idle + total relay timeout (Tier 0.1).** Wrap `io::copy_bidirectional` (src/main.rs:561) in an idle-reset + absolute deadline, and replace bare `set_keepalive(true)` (src/main.rs:585) with `TcpKeepalive` (time 15s/interval 5s/retries 3) + `TCP_USER_TIMEOUT`. *Rationale:* closes a trivial slowloris connection-exhaustion DoS that exists at any scale today; this is the single most dangerous defect.

2. **Remove the reject-path `sleep().await` + default `reject_sleep_ms`→0 (Tier 0.2, src/main.rs:390-392,179).** *Rationale:* one-line change that stops the proxy from throttling its own recovery under exactly the overload it's meant to survive.

3. **RAII `ConnGuard` for the conn slot + unify ordering on `AcqRel` (Tier 0.3, src/main.rs:385/396/418).** *Rationale:* prevents a slow, irreversible capacity bleed-to-total-rejection on any handler panic, and makes graceful shutdown actually complete.

4. **Wire `buffer_size` into the copy path: `copy_bidirectional_with_sizes(... buf, buf)` with a 64 KiB–1 MiB clamp (Tier 1.1, src/main.rs:561).** *Rationale:* ~8x syscall reduction for free, and makes the README's advertised throughput knob real instead of a lie. Highest throughput-per-effort win available without a fork.

5. **Affinity-correct pinning: `sched_getaffinity` → allowed-CPU list, bound-check `CPU_SETSIZE` (Tier 0.4, src/main.rs:94/668-678).** *Rationale:* without it the entire CPU-pinning premise silently breaks under any cgroup/cpuset (every container/k8s deploy) and panics on big-iron — a correctness failure of the core architecture.

If room remains, fold in the trivial **cache-line padding of the four counters (Tier 0.5)** and the **README truthfulness edits (Tier 4.9d)** since both are near-zero-cost.

## 4. Incremental vs. Architectural Fork

**Incremental (keep the current per-worker / current-thread Tokio / SO_REUSEPORT / sched_setaffinity shell):** essentially everything above. The splice(2) zero-copy path (1.2) is notable — it delivers the big memory-bandwidth win *on the existing epoll runtime* via `AsyncFd` over the raw fds the code already exposes, so it is incremental, not a fork. Backend pool, health/failover, metrics, admin endpoint, PROXY protocol, config reload, NUMA mempolicy, SO_INCOMING_CPU, allocator swap, counter sharding — all bolt onto the current architecture.

**Requires an architectural fork:**
- **io_uring data plane (tokio-uring or glommio).** This replaces the per-worker mio/epoll reactor (src/main.rs:327-336) with a completion-based, thread-per-core runtime to get batched submit/complete (syscalls O(packets)→O(batches), ~10-100x), `IORING_OP_SPLICE`, registered buffers, and multishot accept. Glommio also *subsumes* the existing per-core pinning model (src/main.rs:315-360). This is the only change that pushes toward saturating a 100G NIC *per core* rather than per several cores, and it touches the runtime, the accept loop, and the data path — scope it as a separate, deliberate rewrite after the incremental wins land.
- **AF_XDP / kernel-bypass** (one UMEM per NUMA node) is a further fork beyond io_uring, justified only if even io_uring-splice can't hit the 400 Gbps target on the available cores — eliminates per-packet skb allocation entirely. Defer until measurement proves it's needed.

Recommended sequencing: Tier 0 (first PR) → Tier 1 incremental (1.1, 1.3–1.7) → Tier 2 backend pool/health (the actual unblock for "millions") → Tier 3 observability → splice (1.2) → then evaluate the io_uring fork against measured per-core throughput. Do **not** start the io_uring fork before the Tier 0/2 correctness and backend work — a faster data plane on a proxy that self-DoSes via slowloris and caps at 28k upstream conns moves no needle.
